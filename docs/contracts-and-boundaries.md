# Contracts and Integration Boundaries

SFA-5 is a fixture-only setup. The [functional requirements](functional-requirements.md) remain the behavior authority. Schemas and examples are a reviewable starting contract, not proof that feature acceptance has been implemented. The accepted [application architecture](adr/0001-nextjs-application-and-shared-workspace.md) and [contract/trust boundaries](adr/0002-validated-contracts-and-data-trust-boundaries.md) explain the lasting design choices; this guide holds current implementation details.

## Shared package

`@sfa/contracts` exports schemas, inferred types, and provider-neutral internal ports from [`index.ts`](../packages/contracts/src/index.ts). [`fixtures.ts`](../packages/contracts/src/fixtures.ts) is a separate import, `@sfa/contracts/fixtures`; every exported fixture has `{ fixture: true, data }`. Do not strip the marker when exposing a future demo response. Real adapters will not pretend that fixtures are live.

- `Company` contains a durable `companyId` and name. `Listing` references that company and has market, symbol, and a separate exchange identifier. TH/US are product markets, not exchanges. Resolve a routed market/symbol through an identity source before obtaining a complete listing; do not infer exchange from market. Fake exchange identifiers assert no real coverage.
- `Source` retains `sourceAsOf` and `fetchedAt` separately; ISO timestamps require an explicit offset (`Z` is valid). Refreshing data does not change its source timestamp. No arbitrary provider-age threshold is invented.
- `NumericValue` distinguishes available finite values, including zero, from missing null plus a reason. Money carries THB/USD and an explicit unit; non-money units use null currency. `Result` distinguishes available data, unavailable data, and an error. Missing quote fields can coexist with an available quote envelope.
- Shared publications have identity, a date field intended for the Thai publication day, publication time, evidence cutoff, and source timestamps. TH and EN variants sit under one evidence snapshot; this prevents independent snapshot references but cannot prove translation or factual quality. `ThaiDateSchema` validates date syntax, not a timestamp's Bangkok date. `GenerationPort` covers shared-publication text only, not chat. `EvidenceSnapshot` lists sources; it has no retrieved-passage or claim-mapping structure. These need feature work before grounded generation is implemented.

## UI → BFF → adapter

The stock Server Component calls [`research.ts`](../apps/web/src/server/research.ts), which resolves only known fixture routes and calls [`fixture-market-data.ts`](../apps/web/src/server/adapters/fixture-market-data.ts). Unknown routes return 404 without substituting a stock. Internal reads currently use server modules; there are no Route Handlers. Add one only when a feature needs an HTTP interface, validating inputs and results through shared schemas.

To replace the fixture adapter, implement `MarketDataPort`, map a selected provider's actual response into these contracts, validate it, and inject it at the server composition point. Provider SDKs, credentials, response schemas, supported exchanges, and freshness handling need their own verified decisions. No adapter is selected by these port names. The fixture quote returns missing price; there are no realistic prices or returns.

## Shared publication → future worker entry point

`currentDayBriefLookupFixture` demonstrates a current-day display and AI context. `previousDayBriefLookupFixture` demonstrates a dated display fallback with unavailable current-day context. The lookup schema requires available `todayContext` to match `requestedThaiDate`; it does not obtain the actual current date or constrain the display to yesterday. These are fixed examples from 2000, never runtime evidence about today.

`dailyStockSummaryLookupFixture` keys a summary by listing and requested Thai date; the schema checks that an available result matches both. The publication lifecycle required by [FR-03](functional-requirements.md#fr-03-daily-brief-content-and-publication) and [FR-11](functional-requirements.md#fr-11-shared-daily-stock-summary) is absent: no generation, cache, scheduler, database, archive, or refresh logic is implemented.

The [worker boundary and coordination constraints](adr/0001-nextjs-application-and-shared-workspace.md#consequences) are accepted architecture, not an existing entry point. No worker or job infrastructure exists in this scaffold.

[`fixture-generation.ts`](../apps/web/src/server/adapters/fixture-generation.ts) validates a generation request and returns unavailable. It is not called by the page shells. Future consumers must validate generated output, evidence references, language, and factual support, following the [trust boundary](adr/0002-validated-contracts-and-data-trust-boundaries.md).

## Session chat and future private accounts

`chatContextFixture` specifies language, explicit selected-listing association, and a Daily Brief lookup. `sessionHistoryFixture` has a general conversation mentioning a ticker with no stock link and a stock-origin conversation with an explicit listing. Both belong in the main view; only the latter belongs in that listing's stock view. Session-history examples contain user messages only; the separate draft answer fixture below demonstrates citation structure using demo-only text.

`SessionHistorySchema` describes version 1 browser `sessionStorage` data. This is a proposed storage contract only: no persistence implementation, synchronization, multi-tab policy, history UI, or server history store exists. Browser storage, submitted associations, fixture markers, retrieved text, and messages are untrusted. Parsing shape does not authorize a stock binding or establish trusted AI evidence; re-resolve listing identity and today's current publication on the server. Never let old history promote an archived brief into current context.

Phase 1 needs no account. When personal features arrive, enforce authenticated ownership before reading/writing account-private records or building private chat context. Shared publication interfaces must continue to exclude personal input, and private content must stay out of shared outputs, logs, and caches. Authentication, storage, retention/deletion controls, and private cache design are deferred.

## Draft Phase 1 service handoffs

The following names identify logical services, not extra deployments or verified individual assignments. The **Integration Lead / Contracts Package** maintains schemas, fixtures, cross-service compatibility, and producer/consumer checks. Feature owners implement the services inside the accepted web/worker architecture. These additions are draft contracts for review; only the existing fixture adapters run today. No live service, ownership assignment to a person, or provider capability is implied.

- **Market Data Service → Home BFF, Stock Research BFF, AI Tool Service, Publication Worker.** Existing `MarketDataPort` remains compatible; draft `ResearchDataPort` adds indices, price history, statements, metrics, and stock news. `MarketOverviewSchema` requires all five FR-05 index slots, each with its own result. `PriceHistorySchema` identifies the listing and requested 1D/1M/1Y/5Y range, timestamped price/volume points, and provenance. A missing range returns unavailable rather than an empty successful series. `FinancialStatementSchema` identifies statement kind, annual/quarterly reporting period, named rows, units/currency, and provenance. `FinancialMetricsSchema` requires all six FR-12 metric slots, with explicit value/basis/period or unavailable/error. `NewsItemSchema` keeps publication time separate from fetch time and binds relevant listings explicitly. Fixtures: `marketOverviewFixture`, `priceHistoryFixture`, `financialStatementsFixture`, `financialMetricsFixture`, `newsFixture`; existing TH/US identity and quote fixtures remain unchanged. Provider mappings, adjustment conventions, statement-row vocabulary and metric definitions must be agreed with the selected data adapter; this draft invents none.
- **Ingestion Worker → Evidence Retrieval Service → AI Answer Service / Publication Worker.** `IngestionJobSchema` carries configured source IDs, never fetched text or private input. Resolve those IDs against trusted configuration; do not fetch arbitrary browser-supplied URLs. `RetrievedEvidenceSchema` adds passage text, stable passage/source IDs, a document locator, optional explicit listing and reporting period to an evidence snapshot. `RetrievalPort` is the provider-neutral query boundary. Evidence source/passage IDs must be unique and every passage must reference a source in the snapshot. Fixture: `retrievedEvidenceFixture`. Index storage, document extraction, ingestion cadence, and index activation/recovery are unimplemented. Retrieved text remains untrusted even after validation.
- **Browser Chat UI → Chat BFF / AI Answer Service → Browser Chat UI.** `ChatRequestSchema` accepts request/conversation IDs, requested language, an untrusted explicit association, and a message. It accepts no client evidence, publication, portfolio, or profile fields. Re-resolve the association and today's brief server-side before calling retrieval/generation. `ChatPort` returns `ChatResponseSchema`: answered, clarification, unavailable, or error. An answered response uses `GroundedAnswerSchema` with claims referencing passage IDs, dated evidence, language, timestamp, and limitations. The UI renders claims and sources together and stores the resulting display text in the existing session-history contract; evidence from saved history is never trusted for a later request. Fixtures: `chatRequestFixture`, `chatResponseFixture`, `clarificationFixture`, `unavailableChatFixture`. The answered fixture describes only the demo; it asserts no financial fact. Citation-reference validation does not prove that a passage supports a claim. Factual support, scope, prompt-injection controls, language and request-ID correspondence still need service-level checks. Streaming and resource limits are not selected.
- **Scheduler → Publication Worker; Stock Research BFF → Stock Summary Coordinator.** `PublicationJobSchema` distinguishes dated daily-brief and listing/date stock-summary jobs; both use `jobId` for correlation. `IngestionJobSchema` is a separate job kind. Strict job schemas exclude session messages and personal context. Fixtures: `publicationJobFixture`, `stockSummaryJobFixture`, `ingestionJobFixture`. The worker resolves authoritative sources, listing identity, current Bangkok date and publication state. A job ID alone is not an idempotency guarantee: durable coordination must prevent overlapping hourly brief publication and enforce one published summary per listing/Thai day. First-open stock-summary requests stay first-open triggered; this draft does not schedule them. Retry limits, locks, job storage, and execution mode remain unselected.
- **Publication Worker / Stock Summary Coordinator → Publication Store Service → Home BFF, Stock Research BFF, Chat Context Resolver.** Existing `DailyBriefSchema`, `StockSummarySchema`, and their lookups remain the publication outputs. Draft `PublicationReadPort` names their read boundary. `brief()` receives the server's current Thai date and keeps previous-day display fallback separate from today's context; `archive()` returns a dated publication without a chat-context envelope. `summary()` resolves the listing key and returns the listing/day lookup. `BriefFollowUpsSchema` binds bilingual cards to a publication ID and date; fixtures: existing current-day/previous-day/summary lookups and new `briefFollowUpsFixture`. Check a card against today's latest trusted publication before enabling follow-up; archived/fallback cards cannot authorize Q&A. Publish both languages and their common evidence snapshot atomically; failed work preserves the previous successful publication. Store writes, atomic replacement, next-scheduled-update metadata, failure/delay state and concurrency behavior require implementation before FR-03/FR-11 acceptance. No storage/queue API is prescribed by these drafts.
- **Browser Session History Store → Main Chat UI and Stock Chat UI.** Existing `SessionHistorySchema` and `sessionHistoryFixture` are the handoff. Main chat consumes all conversations; stock chat filters by the resolved full listing association, never by ticker text. No personal-history content goes into shared publication or ingestion jobs. Persistence remains unimplemented.

Contract changes must land with producer mapping, consumer parsing/rendering, fixture changes and boundary checks together. Existing `GenerationPort` still returns plain shared-publication text: passage/claim validation for generated publications must be implemented before promoting that output into a publication. These drafts deliberately do not add authenticated features, execution/trading, a provider SDK, a database, or an HTTP/streaming protocol.

## Bilingual webpage design and implementation

The owner clarified FR-21 on 7 November 2026: finish the Phase 1 website in Thai, prepare for English now, and deliver English UI later. UI copy lives in [`th.json`](../apps/web/src/messages/th.json) and [`en.json`](../apps/web/src/messages/en.json), using the same semantic keys. **Web UI Copy / Dictionaries** produces these files; **Web Layout, Home UI, Stock UI and Chat UI** consume them through [`getMessages()`](../apps/web/src/messages/index.ts). Phase 1 always selects Thai. No locale cookie, language selector, translation dependency or runtime translation service is needed.

Add user-facing labels, errors, empty states, metadata and accessibility text to the dictionaries rather than embedding Thai copy in components. Keep keys identical and values nonempty; the key-parity test prevents missing entries. Existing English entries are preparation, not a promise of a reviewed English release. Full English translation review, locale selection and persistence belong to that later release. Keeping dictionary lookup centralized allows that change without rewriting page components. When English UI is enabled, update document language and all UI copy together and preserve the current page/stock identity. Do not silently fall back to Thai for a missing English key.

UI locale, publication language and requested chat language are distinct. Publication consumers select `variants.th` or `variants.en` from the same publication/evidence snapshot; they do not put generated briefs in the UI JSON or regenerate when the locale changes. Chat may default its requested language to the selected UI locale when implemented, but an explicit user request takes precedence. Provider company names, headlines, identifiers and source text retain their original language unless a separate translated field exists; do not silently translate financial evidence or alter dates/currency. Format numbers/dates for the selected locale at display time while preserving their underlying values and explicit `Asia/Bangkok` publication-day meaning.
