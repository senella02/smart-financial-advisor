# สรุปเรื่อง Security, งานเบื้องหลัง และข้อมูลผู้ใช้

อัปเดต 21 พฤศจิกายน 2026  
เทียบกับ branch `setup-project-architecture` ที่ commit `ca92d7e`

เอกสารนี้รวบรวมสิ่งที่อ่านจาก repo ของเรา โค้ดรุ่นพี่ และเอกสารของบริการต่าง ๆ เพื่อใช้คุยเรื่อง architecture ในทีม ยังไม่ได้ทดลองรันหรือวัดประสิทธิภาพ ส่วนที่เป็นข้อเสนอจึงยังไม่ถือว่าตกลงใช้แล้ว

## 1. งานส่วนนี้ต้องตอบอะไร

มีสามเรื่องที่ต้องดูให้ครบ:

- **Security:** จะกันไม่ให้ AI อ่านข้อมูลผิดคน ใช้เครื่องมือเกินสิทธิ์ หรือตอบโดยไม่มีหลักฐานได้อย่างไร
- **งานเบื้องหลังและ RAG:** จะรันงานตามเวลา เตรียมเอกสาร และสร้างสรุปที่ไหน รวมถึงนำ DAG ของรุ่นพี่มาใช้ได้แค่ไหน
- **ข้อมูลผู้ใช้:** จะเก็บ Profile, Portfolio, Watchlist และประวัติแชตไว้ที่ไหน แล้วดึงส่วนไหนมาให้ AI ใช้ในแต่ละคำถาม

ไฟล์นี้เก็บเหตุผลและทางเลือก ส่วนรายละเอียดวิธีทำอยู่ใน [RFC](../rfcs/architecture-security-and-context.md)

## 2. ตอนนี้เราเลือกอะไรไว้แล้ว

เว็บและ API ใช้ Next.js บน Vercel ส่วนข้อมูลถาวรเก็บใน Supabase PostgreSQL งานที่ใช้เวลานาน เช่น อ่าน PDF หรือสร้างสรุป แยกไปรันเบื้องหลัง ไม่ให้ผูกอยู่กับการเปิดหน้าเว็บของผู้ใช้

ในเอกสารล่าสุด Phase 1 กับระบบเต็มวางไว้ต่างกันดังนี้:

| เรื่อง | Phase 1 | ระบบเต็ม |
| --- | --- | --- |
| รันงานเบื้องหลัง | ใช้ Vercel Schedules, Queues และ Functions ตกลงแล้วใน ADR 0006 | เสนอใช้ Airflow สำหรับงานเอกสาร งานย้อนหลัง และสร้างสรุป |
| ค้นเอกสาร | ค้นข้อความใน PostgreSQL พร้อมตัดคำไทย | เสนอใช้ Pinecone ค้นตามความหมาย โดยเก็บข้อความและข้อมูลอ้างอิงใน Supabase |
| บัญชีและข้อมูลส่วนตัว | ใช้แชตได้โดยไม่ล็อกอิน ประวัติอยู่แค่ browser session | มีบัญชีและข้อมูลส่วนตัวตาม requirements ส่วน Supabase Auth ยังเป็นตัวเลือกที่เสนอ |
| Trigger.dev | ไม่ต้องเพิ่มเพื่อทำตามแบบปัจจุบัน | เก็บเป็นทางเลือกสำรองใน ADR 0007 หากต้องเปลี่ยนที่รันงาน |

ดังนั้นตอนนี้ **Phase 1 เริ่มด้วย Vercel ส่วน Airflow/Pinecone เป็นข้อเสนอของระบบเต็ม และ Trigger.dev ยังไม่ได้เลือกใช้** คำว่า Accepted ใน ADR หมายถึงตกลงแล้ว ส่วน Proposed คือยังเสนอให้พิจารณา ไม่ได้หมายความว่าติดตั้งเสร็จหรือทดสอบผ่านแล้ว

## 3. งานเบื้องหลังกับ RAG ทำอะไรบ้าง

Worker คือส่วนที่รันงานเบื้องหลัง เช่น ดาวน์โหลดรายงาน อ่าน PDF หรือสร้างสรุป ส่วน RAG คือการค้นหลักฐานมาให้ AI ใช้ตอบคำถาม เราจึงต้องเตรียมเอกสารให้ค้นได้ก่อน ขั้นเตรียมนี้เรียกว่า ingestion

ตัวอย่างตั้งแต่ได้เอกสารจนตอบคำถาม:

1. ตรวจพบรายงานบริษัทฉบับใหม่จากแหล่งที่เราอนุญาตให้ดึง
2. ดาวน์โหลดและอ่านเนื้อหา ถ้าเป็นภาพสแกนจึงใช้ OCR แปลงเป็นข้อความ
3. แบ่งข้อความเป็นส่วน ๆ พร้อมเก็บว่ามาจากบริษัทไหน งวดไหน หน้าไหน และ URL อะไร
4. เตรียมให้ค้นข้อความได้ ถ้าจะค้นตามความหมายก็สร้าง Embedding ซึ่งเป็นชุดตัวเลขแทนความหมายของข้อความเพิ่ม
5. เมื่อผู้ใช้ถาม ระบบค้นเฉพาะเอกสารที่ตรงบริษัทและช่วงเวลา แล้วส่งให้ AI ตอบพร้อมอ้างอิง

จุดที่ต้องระวังคือ ค้นเจอไม่ได้แปลว่าใช้ตอบได้เสมอ ถ้าได้เอกสารผิดบริษัท ผิดงวด หรือระบุเลขหน้าผิด คำตอบก็ยังผิดได้ แม้จะมีลิงก์อ้างอิงก็ตาม

### ใครเริ่มงาน ใครรันงาน และใครเก็บสถานะ

| ส่วน | ทำอะไร | ตัวอย่างใน Phase 1 |
| --- | --- | --- |
| ตัวตั้งเวลา | สั่งเริ่มตามรอบ | Vercel Schedules สั่งตรวจข่าว |
| คิว | รับงานไว้รอประมวลผล | Vercel Queues รับรหัสงาน |
| Worker | รันโค้ดที่ทำงานจริง | Vercel Functions ดึงข้อมูลหรือสร้างสรุป |
| ฐานข้อมูล | เก็บสถานะและผลที่ต้องรักษา | Supabase เก็บว่างานไหนรอ สำเร็จ หรือต้องทำใหม่ |

เลือก Cron อย่างเดียวจึงยังไม่ครบ ต้องรู้ด้วยว่าจะรันโค้ดที่ไหน และถ้าเครื่องหยุดหรืองานพังจะทำต่ออย่างไร

### ตารางงานที่ตกลงแล้ว

| งาน | รอบที่กำหนด |
| --- | --- |
| ตรวจข่าว | ทุกชั่วโมงที่นาที `:00` และ `:30` เวลากรุงเทพฯ |
| Daily Brief | ทุกชั่วโมงที่นาที `:25` รวมวันหยุด ใช้ข่าวชุดล่าสุดที่เตรียมเสร็จตอนเริ่มสร้าง |
| ตรวจ filings สหรัฐฯ | ทุกชั่วโมง ตั้งแต่ 06:00–23:00 วันทำงาน ตามเวลา New York |
| ตรวจ filings ไทย | 09:00, 14:00 และ 22:00 วันทำงาน เวลากรุงเทพฯ |
| สรุปหุ้นรายวัน | เริ่มเมื่อมีคนเปิดหุ้นนั้นครั้งแรกของวันตามปฏิทินไทย สร้างสำเร็จแล้วใช้ฉบับเดิมทั้งวัน |

เวลาตามตารางกับเวลาที่งานเริ่มจริงอาจต่างกัน ต้องเผื่อเวลารอคิวและเวลาประมวลผลด้วย รายละเอียดอยู่ใน [FR-03, FR-11 และ FR-12](../final/functional-requirements.md)

### Daily Brief ของ Phase 1 กับ Phase 2 ต่างกันตรงไหน

Phase 1 สรุปข่าวจากแหล่งที่อนุญาตในชุด pilot ก่อน ส่วน Phase 2 เพิ่มภาพรวมตลาดพร้อมเวลาของราคา และให้ค้นรายงานบริษัทประกอบข่าวที่เลือกได้ เช่น ถ้าเลือกข่าวผลประกอบการของบริษัทหนึ่ง ก็อ่านตัวเลขจากรายงานของบริษัทนั้นมาอธิบายเพิ่มได้

การค้นเพิ่มต้องจำกัดทั้งจำนวนครั้งและเวลาที่ใช้ ตรวจบริษัท งวด และวันเผยแพร่ก่อนนำมาใช้ แล้วกำหนดชุดหลักฐานให้เรียบร้อยก่อนสร้างทั้งสองภาษา ขั้นสร้างคำตอบสุดท้ายไม่เปิดให้ค้นเพิ่ม เพื่อให้ไทยและอังกฤษใช้ข้อมูลชุดเดียวกัน

หากข้อมูลตลาดหรือรายงานบางส่วนไม่พร้อม ยังเผยแพร่ส่วนที่มีหลักฐานรองรับได้ แต่ต้องบอกว่าขาดอะไร และไม่สรุปว่าข่าวเป็นสาเหตุให้ราคาขยับถ้าไม่มีหลักฐานยืนยัน จำนวนครั้งที่ค้นและเวลาสูงสุดยังต้องกำหนดใน Q08 [ข้อกำหนด Daily Brief](../final/functional-requirements.md#fr-03-daily-brief-content-and-publication) · [Workflow ที่เสนอ](../rfcs/ai-workflow-orchestration.md#three-workflow-shapes)

## 4. DAG ของรุ่นพี่เอามาใช้ได้ไหม

ใช้เป็นต้นแบบขั้นตอนได้ และอาจนำฟังก์ชันบางส่วนมาปรับใช้ แต่ยังยกมารันกับของเราตรง ๆ ไม่ได้

DAG คือการกำหนดลำดับว่าแต่ละงานต้องรออะไร เช่น ต้องดาวน์โหลดเสร็จก่อนอ่าน PDF และต้องได้ข้อความก่อนสร้าง Embedding ส่วน Airflow เป็นระบบที่ใช้ตั้งเวลา รัน และดูสถานะงานเหล่านี้

โค้ดที่ตรวจคือ [LLMFA commit `a067931`](https://github.com/llmfa-capstone/llmfa-capstone/tree/a067931aa95f9c29f0f7a3bc51bea25f0b2fe4d2) ยังไม่ได้ทดลองรันระบบของรุ่นพี่

### รุ่นพี่ทำไว้อย่างไร

ใน `llmfa_airflow/dags/llmfa_dag.py` มีงานชื่อ `llmfa_monthly_pipeline` รันวันที่ 1 ของทุกเดือน และไม่ไล่รันรอบย้อนหลังที่ขาดไปเอง ขั้นตอนหลักคืออ่านแหล่งข้อมูล → ดาวน์โหลด → แปลง HTML/PDF เป็น Markdown → แบ่งข้อความ → สร้าง Embedding → ส่งเข้า Pinecone → รายงานผล

PDF ใช้ Typhoon OCR ส่วน Embedding ใช้ Gemini มีการแยกกลุ่มงานตามแหล่งข้อมูล แต่ข้างในยังวนทำทีละไฟล์ผ่านฟังก์ชันย่อย ไม่ใช่ทุกไฟล์มี Airflow task แยกให้ดูสถานะหรือสั่งทำใหม่ได้เอง

ตารางรายเดือนของรุ่นพี่ไม่ตรงกับข่าวและ filings ของเรา จึงต้องปรับรอบดึงข้อมูล และไม่ควรดาวน์โหลดทุกอย่างใหม่ทุกครั้ง

### จุดที่ต้องแก้ก่อนนำมาใช้

| สิ่งที่พบ | ถ้านำมาใช้กับเรา ต้องระวังอะไร |
| --- | --- |
| ล้างโฟลเดอร์ดาวน์โหลดก่อนเริ่ม และส่งตำแหน่งไฟล์ในเครื่องระหว่างขั้น | ถ้าเครื่องหยุดหรือย้ายเครื่องอาจไม่มีไฟล์ให้ทำต่อ ต้องเก็บไฟล์ที่จำเป็นไว้ถาวรและจำว่าทำถึงขั้นไหน |
| หลายขั้นจับข้อผิดพลาดแล้วคืนค่า error | Airflow อาจมองว่างานจบแล้ว ไม่สั่งทำใหม่ ต้องแยกงานสำเร็จ งานไม่ครบ และงานล้มเหลว |
| สร้างรหัสเอกสารจากชื่อไฟล์ | ชื่อซ้ำหรือเอกสารฉบับแก้ไขอาจแยกกันไม่พอ ต้องเก็บแหล่งที่มาและรุ่นของเนื้อหา |
| จับคู่หน้าไม่ได้แล้วใช้หน้าแรก | อาจอ้างผิดหน้า ถ้าหาไม่ได้ต้องระบุว่าไม่ทราบ |
| ใช้วันที่สร้าง PDF เป็น metadata | วันที่สร้างไฟล์ไม่ใช่วันเผยแพร่หรืองวดบัญชี ต้องเก็บแยกกัน |
| ส่งข้อมูลเข้า Pinecone ได้ไม่ครบ แต่ยังคืน success พร้อมจำนวนที่สำเร็จ | ต้องตรวจว่าครบและค้นได้ก่อนเปิดใช้เอกสารรุ่นใหม่ ไม่ดูแค่สถานะ success |

อ้างอิงโค้ด: [DAG](https://github.com/llmfa-capstone/llmfa-capstone/blob/a067931aa95f9c29f0f7a3bc51bea25f0b2fe4d2/llmfa_airflow/dags/llmfa_dag.py), [Embedding helper](https://github.com/llmfa-capstone/llmfa-capstone/blob/a067931aa95f9c29f0f7a3bc51bea25f0b2fe4d2/llmfa_airflow/libs/embedding.py)

เรื่องข้อมูลผู้ใช้ก็ต้องปรับ ใน [Backend handlers ที่อ่าน](https://github.com/llmfa-capstone/llmfa-capstone/blob/a067931aa95f9c29f0f7a3bc51bea25f0b2fe4d2/llmfa_backend/main.py) มีการอ่าน conversation ด้วย ID และอ่านรายการแชตโดยไม่เห็นการตรวจเจ้าของใน handler นั้น เราจึงไม่ควรใช้การส่ง ID มาอย่างเดียวเป็นสิทธิ์อ่านข้อมูล ข้อนี้เป็นข้อสังเกตจากไฟล์ที่ตรวจ ไม่ได้ยืนยันว่า deployment ของรุ่นพี่ไม่มีการป้องกันจากส่วนอื่น

ส่วนที่น่าต่อยอดคือขั้นดาวน์โหลด แยกวิธีอ่าน HTML/PDF แบ่งข้อความ และสร้างดัชนี แต่ต้องลองกับรายงานไทยและสหรัฐฯ ของเรา โดยเฉพาะตารางงบและตำแหน่งอ้างอิง การใช้ฟังก์ชัน Python บางส่วนไม่ได้บังคับให้ยก backend หรือฐานข้อมูลเก่ามาด้วย และต้องตรวจ dependencies กับ license ก่อนใช้โค้ด

## 5. ถ้าไม่ใช้ Trigger.dev มีทางไหนอีก

| ทางเลือก | ข้อดีสำหรับเรา | สิ่งที่ต้องดูเพิ่ม |

| Vercel Schedules + Queues + Functions | อยู่บนบริการเดียวกับเว็บ และเลือกไว้สำหรับ Phase 1 แล้ว | งานรันทันข้อจำกัดเวลาหรือไม่ รอคิวนานแค่ไหน และใช้โควตาเท่าไร |
| Trigger.dev Cloud | มีตัวช่วยตั้งเวลา ทำใหม่เมื่อพลาด จำกัดงานพร้อมกัน และดูสถานะงาน TypeScript | เพิ่มบริการอีกชุด ต้องตรวจแผนและค่าใช้จ่าย |

| Supabase Cron + Worker | ใช้ฐานข้อมูลเดิมตั้งเวลาเรียกงาน | ยังต้องมีที่รัน Worker จริง Cron ไม่ได้ทำ OCR หรือ Embedding ให้เอง |
| GitHub Actions / Worker บน VM | ใช้ทดลองงานเป็นรอบหรือสั่งรันเองได้ | ต้องดูเรื่องเวลาเริ่มงาน การทำใหม่ และ secrets ถ้าใช้ VM ทีมต้องดูแลเครื่องด้วย |

ไม่ว่าใช้ทางไหน Supabase ยังต้องจำสถานะงานและกันผลซ้ำ เช่น คนเปิดหุ้นเดียวกันพร้อมกันไม่ควรได้สรุปหลายฉบับ และงานเก่าที่เสร็จช้าต้องไม่ทับผลใหม่ การเลือก runner อย่างเดียวไม่ได้จัดการเรื่องนี้ให้ครบ

รายละเอียดและเอกสารบริการ: [ผลเปรียบเทียบบริการ](final-architecture-service-options.md#background-execution-for-the-final-version), [Vercel](https://vercel.com/docs/schedules), [Cloud Run Jobs](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule), [Airflow](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/overview.html), [Supabase Cron](https://supabase.com/docs/guides/cron), [GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

### Trigger.dev ฟรีได้ไหม

[ราคา ณ วันที่ตรวจ 21 พฤศจิกายน 2026](https://trigger.dev/pricing) ระบุ Free $0/เดือน มีเครดิต $5/เดือน รันพร้อมกันได้ 20 งาน ตั้งได้ 10 schedules และเก็บ logs 1 วัน เครดิตนี้มีจำกัด และไม่รวมค่าโมเดล ฐานข้อมูล OCR/Embedding หรือที่เก็บไฟล์จากบริการอื่น

ข้อจำกัดที่กระทบเราโดยตรงคือ [schedule ที่สร้างขณะใช้ Free](https://trigger.dev/docs/tasks/scheduled#free-plan-minimum-window) รันได้ไม่ถี่กว่าชั่วโมงละครั้ง และมีช่วงกระจายเวลาเริ่มงานอย่างน้อย 60 นาที จึงไม่ควรคาดว่าจะเริ่มตรงนาทีที่ตั้งไว้ และไม่ตรงกับข่าวที่เราต้องตรวจทุก 30 นาที

## 6. Security ต้องกันอะไรบ้าง

การเขียนใน prompt ว่า “ห้ามเปิดข้อมูล” ไม่พอ ต้องจำกัดสิ่งที่ระบบยอมให้ทำจริงด้วย

### ก่อนอ่านข้อมูล

Server ต้องตรวจรูปแบบคำขอ ขนาดข้อความ session และเจ้าของข้อมูล ไม่เชื่อ user ID หรือ conversation ID ที่ browser ส่งมาอย่างเดียว เช่น ผู้ใช้ A รู้ ID แชตของ B ก็ยังต้องอ่านไม่ได้

Worker ที่สร้างสรุปสาธารณะต้องไม่มีสิทธิ์อ่าน Profile หรือ Portfolio ตั้งแต่บัญชีฐานข้อมูลที่ใช้ ไม่ต้องรอให้ AI ตัดสินใจว่าจะอ่านหรือไม่

Supabase มี RLS สำหรับกำหนดว่าผู้ใช้เห็นข้อมูลแถวไหน แต่บัญชีสิทธิ์สูงบางแบบข้ามกฎนี้ได้ จึงต้องตรวจสิทธิ์ของ connection ที่เว็บและ Worker ใช้ด้วย [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

### แยกประเภทคำถามก่อนค้นข้อมูล

RFC ล่าสุดเสนอให้ Phase 2 มีขั้นตรวจว่าผู้ใช้กำลังถามอะไร ก่อนเริ่มค้นหลักฐาน ใช้โมเดลแชตตัวเดิม แต่ไม่เปิดเครื่องมือให้เรียกในขั้นนี้ เช่น:

| คำถาม | สิ่งที่ระบบทำต่อ |
| --- | --- |
| “ผลประกอบการล่าสุดเป็นอย่างไร” บนหน้า AAPL | ใช้หุ้นที่หน้าเว็บระบุไว้ แล้วค้นหลักฐานของ AAPL |
| “อยากรวยทำไง” | ถามเพิ่มว่าต้องการศึกษาหุ้นหรือเรื่องไหน ยังไม่ค้นข้อมูล |
| ขอให้สร้างภาพ | แจ้งขอบเขตของแชตและชวนกลับมาที่การศึกษาหุ้น ไม่ค้นข้อมูลการเงิน |

โมเดลช่วยแยกประเภท แต่ Server เป็นคนตรวจผลและเลือกขั้นตอนถัดไป ถ้าผลไม่ถูกต้องหรือขั้นนี้ล้มเหลว ให้แจ้งว่าลองใหม่ได้โดยยังไม่ค้นหลักฐาน ไม่ปล่อยผ่านไปค้นเอง

ต้องตรวจข้อมูลที่อนุญาตให้ส่งไปยังผู้ให้บริการโมเดลก่อนขั้นนี้ด้วย เมื่อคำถามเข้าสู่การค้นข้อมูลการเงินจริง จึงดึง Daily Brief ของวันนี้และข้อมูลส่วนตัวที่อนุญาตมาประกอบ แล้วตรวจอีกครั้งก่อนส่งต่อ ขั้นนี้ช่วยคุมขอบเขตคำถาม แต่ไม่ได้แทนการตรวจสิทธิ์ของเครื่องมือ [Chat workflow](../rfcs/ai-workflow-orchestration.md#three-workflow-shapes)

### ตอน AI เรียกเครื่องมือ

ให้เรียกได้เฉพาะเครื่องมือที่กำหนด เช่น อ่านราคา อ่านงบ ค้นข่าว และค้นเอกสาร แต่ละเครื่องมือต้องตรวจบริษัท งวด และสิทธิ์อีกครั้ง ไม่ให้ AI สร้าง SQL รันคำสั่งเครื่อง ดึง URL อะไรก็ได้ หรือแก้จำนวนหุ้นเอง

เอกสารที่ค้นมาอาจมีข้อความหลอกให้ AI เปลี่ยนคำสั่งหรือเปิดเผยข้อมูล เรียกว่า prompt injection ข้อความในเอกสารต้องไม่มีสิทธิ์เปลี่ยนกฎของระบบ การแยกคำสั่งกับเนื้อหาช่วยได้ แต่ยังต้องจำกัดเครื่องมือและสิทธิ์ด้วย code [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

### ก่อนส่งคำตอบ

ต้องตรวจทั้งว่าอ้างเอกสารที่มีจริง และเอกสารนั้นรองรับคำตอบจริง ตัวอย่างเช่น ลิงก์รายงานอาจถูก แต่ตัวเลขที่ AI ใช้เป็นคนละงวด จึงต้องตรวจบริษัท งวด หน่วย และรุ่นเอกสารด้วย ตัวเลขที่คำนวณได้ควรใช้ code คำนวณ ถ้าหลักฐานไม่พอต้องบอกว่าขาดอะไร ไม่เติมเอง

หน้าเว็บต้องไม่รัน code จากคำตอบและต้องกรองลิงก์ที่ไม่ปลอดภัย พร้อมจำกัดจำนวนคำขอและงานที่รันเพื่อควบคุมการใช้งานและค่าใช้จ่าย การตรวจคำตอบก็ยังผิดได้ ต้องมีชุดทดสอบไทยและอังกฤษ ไม่ถือว่ามี citation แล้วผ่านทันที

### ก่อนส่งข้อมูลออกนอกระบบ

[Gemini Unpaid Services](https://aistudio.google.com/docs/terms) ห้ามส่งข้อมูลส่วนบุคคล ข้อมูลลับ หรือข้อมูลอ่อนไหวเข้าไป แม้ไม่มีบัญชี ผู้ใช้ก็อาจพิมพ์ข้อมูลส่วนตัวลงแชตเองได้ จึงต้องตรวจทั้งคำถามและ history ไม่ใช่แค่ Profile ที่บันทึกไว้ การขอ consent ไม่ได้ยกเลิกข้อห้ามของบริการ

Logs ก็ต้องระวัง ไม่ควรเก็บข้อความดิบหรือบริบทส่วนตัวเพียงเพื่อให้แก้ปัญหาง่ายขึ้น เกณฑ์ก่อนเปิดใช้งานที่ตกลงแล้วอยู่ใน [Phase 1 requirements](../phase-1-planning/functional-requirements.md#release-acceptance) ตอนนี้ยังไม่มีผลทดสอบใหม่ยืนยันว่าผ่านทุกข้อ

## 7. ข้อมูลผู้ใช้เก็บที่ไหน แล้ว AI จะเอาไปใช้อย่างไร

Profile ช่วยให้ตอบเหมาะกับผู้ใช้ เช่น ระดับประสบการณ์หรือความเสี่ยงที่รับได้ ส่วน Portfolio และ Watchlist บอกว่าผู้ใช้ถือหรือติดตามอะไร ข้อมูลพวกนี้เป็นข้อมูลส่วนตัว ต่างจากข่าวและรายงานบริษัทที่ใช้ร่วมกันได้

### ทางเลือกที่เก็บ

| ที่เก็บ | เหมาะกับอะไร | ข้อจำกัด |
| --- | --- | --- |
| ตารางใน PostgreSQL | Profile, holdings, Watchlist และการอนุญาตใช้ข้อมูล ตรวจเจ้าของ แก้ ลบ และอ่านค่าล่าสุดได้ | ต้องออกแบบตารางและสิทธิ์ แต่ใช้ Supabase ที่เลือกไว้แล้วได้ |
| Document database เช่น MongoDB | ข้อมูลยืดหยุ่นหรือซ้อนหลายชั้น | เพิ่มฐานข้อมูลและงานดูแลสิทธิ์/การลบอีกชุด |
| Vector database | ค้นข้อความตามความหมาย | ไม่เหมาะเป็นแหล่งหลักของจำนวนหุ้น ต้นทุน หรือสิทธิ์ล่าสุด และต้องไม่ปนข้อมูลส่วนตัวกับดัชนีสาธารณะ |
| Browser session | ประวัติชั่วคราวใน Phase 1 | ไม่ใช่ข้อมูลถาวรข้ามอุปกรณ์ และข้อความที่ส่งกลับมาต้องตรวจ |

โปรเจกต์เลือก PostgreSQL เป็นฐานข้อมูลถาวรแล้วตาม ADR 0005 การมี Profile/Portfolio จึงไม่ได้ทำให้ต้องเพิ่มฐานข้อมูลอีกตัว ส่วนรายละเอียดตารางอยู่ใน RFC

### ตัวอย่างการดึงมาใช้

สมมติผู้ใช้ถามว่า “พอร์ตที่แนบมากระจุกตัวในหุ้นไหนบ้าง” การเก็บพอร์ตในฐานข้อมูลไม่ได้ทำให้ AI รู้เอง ต้องมี Server ดึงข้อมูลให้ตามขั้นตอนนี้:

1. ตรวจว่าเป็นผู้ใช้คนไหน และแนบ Portfolio มาให้ใช้กับคำถามนี้หรือไม่
2. อ่านเฉพาะ holdings ของเจ้าของบัญชีนั้น
3. คำนวณมูลค่าและสัดส่วนด้วย code ใช้ราคาและ FX ตามกติกาเดียวกับหน้า Portfolio
4. เลือกส่งเฉพาะข้อมูลที่จำเป็น พร้อมเวลาของข้อมูล ให้ AI ช่วยอธิบาย
5. ตรวจคำตอบ และไม่เอาบริบทส่วนตัวไปเก็บในสรุปหรือ cache ที่คนอื่นใช้ร่วมกัน

ข้อมูลที่เปลี่ยนบ่อยอย่างจำนวนหุ้นหรือต้นทุนจึงมาจากค่าปัจจุบันในฐานข้อมูล ไม่ใช่ความจำของ AI ส่วน Profile ใช้ปรับวิธีตอบ ไม่ใช่หลักฐานยืนยันข้อเท็จจริงตลาด

### กติกาข้อมูลส่วนตัวที่ตกลงแล้ว

| เรื่อง | กติกาปัจจุบัน |
| --- | --- |
| Phase 1 | ไม่มี saved Profile/Portfolio และเก็บแชตเฉพาะ browser session |
| Profile ในระบบเต็ม | กรอกหรือไม่ก็ได้ ปิดการใช้กับ AI ไว้เป็นค่าเริ่มต้น |
| Watchlist/Portfolio | แนบแยกแต่ละคำถาม เคยแนบครั้งก่อนไม่ได้แปลว่าใช้ต่อได้ |
| ปิด Profile | ตัดทั้งข้อมูลใหม่และข้อความเก่าหรือบทสรุปที่เปิดเผยข้อมูลนั้นออกจากคำขอ AI ถัดไป |
| Saved chats | ผู้ใช้เลือกบันทึกเอง หมดอายุ 90 วันหลังข้อความสุดท้าย และลบก่อนได้ |
| ลบ Profile | แชตที่ยังไม่หมดอายุเปิดดูได้ แต่ไม่ใช้รายละเอียด Profile ในคำขอ AI ต่อ ลบบทสรุปที่สกัดไว้ และให้เลือกการลบแชตที่เกี่ยวข้อง |
| ลบบัญชีและกู้ข้อมูลสำรอง | ลบ Profile และ saved chats ข้อมูลสำรองที่แอปควบคุมเก็บไม่เกิน 30 วัน ต้องใช้กฎการลบ/หมดอายุก่อนเปิดข้อมูลที่กู้คืน |

ถ้าปิด Profile แล้วหยุดอ่านตารางใหม่อย่างเดียว แต่ยังส่งแชตเก่าที่มี Profile อยู่เข้า AI ก็ยังใช้ข้อมูลนั้นอยู่ เช่นเดียวกับ Portfolio ที่แนบครั้งก่อน ต้องตรวจ history และบทสรุปด้วย

กติกานี้อัปเดตแล้วใน [Q07](../requirements-questions.md#q07-personalization-and-personal-data-controls) และ FR-14/17/20 ไม่ควรเขียนว่ายังรอตกลงทั้งหมด ส่วนวิธีล็อกอิน บริการโมเดลสำหรับข้อมูลส่วนตัว และการใช้ข้อมูลข้ามอุปกรณ์บางส่วนยังต้องสรุป

## 8. เหลืออะไรที่ต้องคุยหรือทดลอง

Phase 1 เลือก Vercel แล้ว รอบตรวจข่าว/filings และกติกาข้อมูลส่วนตัวก็มีใน requirements แล้ว จึงไม่ต้องเริ่มตัดสินใจเรื่องพวกนี้ใหม่จาก Research นี้ ส่วน Airflow/Pinecone ในแบบระบบเต็ม และ Trigger.dev ใน ADR 0007 ยังเป็นข้อเสนอ

สิ่งที่ยังต้องทำคือทดลองกับข้อมูลจริงและวัดว่าแบบที่วางไว้ทำได้แค่ไหน:

- อ่านรายงานไทย/สหรัฐฯ และตารางงบได้ถูกต้องหรือไม่
- คำถามไทยค้นหลักฐานภาษาอังกฤษได้ดีแค่ไหน
- ขั้นแยกประเภทคำถามถามเพิ่มหรือหยุดก่อนค้นได้ถูกต้องทั้งไทยและอังกฤษหรือไม่ และเพิ่มเวลา/ค่าใช้จ่ายเท่าไร
- Daily Brief ของ Phase 2 ใช้ข้อมูลตลาดและรายงานได้ถูกบริษัท งวด และเวลาหรือไม่ เมื่อค้นไม่สำเร็จหรือครบจำนวนที่จำกัดไว้ ยังรายงานส่วนที่มีหลักฐานได้หรือไม่
- ผู้ใช้คนหนึ่งอ่านข้อมูลอีกคนไม่ได้จริงหรือไม่ และ Worker สาธารณะอ่านข้อมูลส่วนตัวไม่ได้จริงหรือไม่
- เอกสารที่มีคำสั่งหลอกทำให้ระบบใช้เครื่องมือเกินสิทธิ์ได้หรือไม่
- งานซ้ำ งานพัง หรือเครื่องหยุดแล้วกู้คืนได้ โดยไม่ทับผลสำเร็จล่าสุดหรือเปิดเอกสารที่เตรียมไม่ครบหรือไม่
- ปิดใช้ข้อมูลส่วนตัวแล้วข้อมูลนั้นยังย้อนมาทาง history หรือ cache หรือไม่
- งานรันทันเป้าหมายและอยู่ในงบหรือไม่ โดยต้องกำหนดตัวเลขใน Q08

Pilot เริ่มจาก AAPL, JPM, WMT, ADVANC, KBANK และ PTT ตาม Phase 1 requirements แต่ยังต้องตรวจสิทธิ์เก็บและใช้ข้อมูลแต่ละแหล่ง การมี pilot ไม่ได้ยืนยันว่าขยายไปทุกบริษัทหรือทุกแหล่งข่าวได้แล้ว

อ่าน [RFC](../rfcs/architecture-security-and-context.md) ต่อเมื่อต้องการดูวิธีทำที่เสนอ และอ่าน [แบบระบบเต็ม](../final/final-architecture.md) เพื่อดูการเชื่อมทั้งระบบ ส่วน [ADR 0007](../adr/0007-managed-worker-execution.md) พูดเฉพาะทางเลือก Trigger.dev ไม่ได้ตัดสินทุกเรื่องในงานนี้ รายละเอียดบริการและแหล่งอ้างอิงเพิ่มเติมอยู่ใน [service research](final-architecture-service-options.md)
